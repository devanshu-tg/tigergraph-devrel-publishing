Where an Agent Earns Its Tokens — Agentic GraphRAG over TigerGraph

Description:- 
Four pipelines answer the same 150 Olympic-event questions over one TigerGraph graph, with Qwen3.8-27B serving every pipeline including the planner and the verifier. Only LLM tokens are counted; GSQL and Python cost nothing.

Public split: RAG 30% → GraphRAG 89% → Agentic 100% → Structured control> 100% at 0 tokens. The agentic pipeline is simultaneously the most accurate and the cheapest of the three generative ones — 552 tokens/question against GraphRAG's 1,694 (67% fewer tokens for 11 points more accuracy) and RAG's 1,284 (57% fewer for 70 points). 0 error rows across all 8 result files.

The finding is not that agents score better. It is why, measured: the 150 questions come from five templates, and four are structured database queries wearing question marks. Chunk retrieval cannot count and cannot take an argmax, so RAG collapses on exactly the two templates that need arithmetic over a set (aggregation 5%, superlative 20%) and is respectable on the single-document one (lookup 63%). GraphRAG fixes the aggregate by projecting structured rows; the agent adds the ability to choose which projection a question needs.

We also report the result that cuts against us: a deterministic control solves all 150 at zero tokens. That is not a baseline to beat — it is the routing-boundary oracle, and it is what makes the agentic pipeline's token count a measured saving rather than a claim. Because the questions are templated, no question defeated the regex router, so changed_strategy is 0/100: the agent runs multi-step plans and gets them right, but recovery from a bad first step is untested and we do not claim it works.

Engineering: 2,210 typed Event vertices and 25,380 embedded chunks in TigerGraph 4.2, selection and aggregation executed server-side in interpreted GSQL (one installed query, because vectorSearch() is refused in interpreted mode). 74 regression tests, stdlib unittest, needing neither TigerGraph nor the LLM endpoint — so the suite runs when the tunnel is down, which on this deployment is often. Those tests caught five real bugs, including a scorer that credited a one-character answer and an extractor that returned a whole sentence where a bare number was due.

## Details

- **LLM:** Qwen3.8-27B-UD-Q4_K_M.gguf (reasoning trace enabled), served via an OpenAI-compatible /v1 endpoint. The same model instance served all four pipelines — including the agentic orchestrator's planner and its verifier, not just the answer-generation step. No separate router, planner or summarizer model was used.
- **Vector database:** TigerGraph's own native vector index — no external vector DB. All 25,380 chunks are stored as Chunk vertices carrying a vector attribute declared as embedding(Dimension=1024, IndexType="HNSW", DataType="FLOAT", Metric="COSINE"), retrieved with TigerGraph's vectorSearch() function. Embeddings generated by Qwen3-Embedding-0.6B (1024-dim, L2-normalised).
- **Graph backend:** TigerGraph Savanna (Enterprise) — release_4.2.5_08-26-2026
- **Average agent steps per question:** 2.95 (1.95 tool calls + 1.00 LLM planner calls)
- **Retrieval methods:** 1. Dense vector similarity search — TigerGraph's native vectorSearch() over Chunk vertices (HNSW index, 1024-dim, COSINE metric, top-8), executed through vs_chunks, the only installed query in the system. 2. Template/regex question parsing — 5 question templates reduced to a typed QuestionSpec. Zero LLM tokens. 3. Entity linking — sport phrase → Sport vertex (biathlon → Biathlon), plus venue-prefix matching and in-text sport resolution for temporal questions where the sport sits inside the event description. 4. Multi-hop graph traversal — 1–2 hop typed traversals: Event→IN_GAMES→Games, Event→HELD_AT→Venue, Event→IN_SPORT→Sport, Event→WON_MEDAL→Athlete, Event→PRECEDED_BY→Event. 5. Server-side filtering and aggregation — counts, thresholds and argmax pushed down into interpreted GSQL as predicates, so aggregation happens in the database rather than by post-filtering rows in Python. 6. Date-containment filtering — eight distinct date formats normalised and matched in Python, because GSQL v2 cannot express the containment/rank-by-tightness comparison. 7. Deterministic ranked event selection — a shared ladder: token match → gender guard → literal name match → specificity → doc_id, used to disambiguate near-duplicate event names. 8. LLM answer generation — one grounded call over the retrieved evidence, with an explicit UNKNOWN escape hatch. The agentic pipeline adds a verifier sufficiency check that can send the orchestrator back to planning. No external vector database, no web search, no external retriever — all retrieval is TigerGraph plus the corpus.
